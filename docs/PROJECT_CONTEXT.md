# Project Context

## 1. Project Mission

项目为什么存在？

跨境电商团队拥有订单数据，但常常缺少统一口径、可信解释和能继续处理的经营结论。CrossBorder AI Analytics 要把原始交易数据转化为可追溯、可复算、可行动的经营判断，而不只是生成图表或模板报告。

解决什么问题？

系统负责数据理解与质量评估，计算经营指标，定位销售、商品、客户、市场、利润和退货变化，并用明确周期、公式、样本和来源字段支撑结论。证据不足时必须降级或停止，不用 Mock、随机数或模板文案补齐结论。

目标用户是谁？

主要用户是进行周报、月报和经营复盘的跨境电商运营负责人及管理者；数据分析师需要核对口径、质量和证据。当前产品面向本地单用户、创业 Demo 和未来受控 AI Agent 场景。

---

## 2. Product Goal

当前产品目标：

在 AutoClean 通用数据底座和可信分析对象链路之上，将 CrossBorder 建成可独立安装、可稳定验证、可解释且能进入人工处置闭环的本地经营分析产品。React + FastAPI 是当前主产品界面，Streamlit 保留用于兼容与业务口径对照。

核心价值：

原始数据只读；指标口径公开；同屏周期一致；所有判断绑定真实数据和证据；用户能从经营摘要进入异常、驱动、建议、任务和对象明细；缺少关键数据时明确说明不能回答什么。

当前阶段：

3.0 Web 产品已形成固定的经营总览、专题分析、数据中心和 AI 分析师四页导航。经营总览和专题分析已按参考设计完成首轮重构与浏览器验收；当前重点是用真实经营案例校准判断、完成全量回归和工程化收口，而不是继续扩张页面或堆叠 AI 文案。

## 4. Technical Architecture

技术栈：

Python 3.10+、pandas、NumPy、SQLite、FastAPI、Uvicorn、React 18、TypeScript、React Router、TanStack Query、ECharts、Radix UI、TailwindCSS、Vitest、pytest 和 Playwright。Streamlit、Plotly 与 Matplotlib 继续支撑兼容界面和历史报告。

模块关系：

AutoClean 提供读取、契约、质量、上下文和基础存储能力；`crossborder_analytics` 提供跨境电商语义、指标、规则、诊断、建议、证据、洞察、机会和报告；`crossborder_api` 将同一分析服务封装为 Web API、状态和 Agent 工具；`frontend` 消费稳定 DTO 构建四页产品；`app.py` 保留 Streamlit 兼容入口。

数据流：

只读原始文件 → AutoClean 规范化分析视图 → SQLite 与受控 SQL → `MetricSnapshot` → `Anomaly` → `DiagnosisResult` → `Recommendation` → `EvidenceBundle` → `InsightView / Opportunity / ActionItem` → FastAPI → React 页面、任务和报告。前端不自行猜测结论，只格式化后端返回的结构化判断。

关键组件：

- `crossborder_analytics/service.py`：分析上下文、筛选、传统模块与可信分析链路编排。
- `crossborder_analytics/database.py` 与 `sql/`：版本化订单、命名参数查询和事实来源。
- `metrics.py`、`anomalies.py`、`diagnosis.py`、`recommendations_v2.py`、`evidence.py`、`insights.py`：确定性分析引擎。
- `decision.py`、`decision_brief.py`、`opportunities.py`：经营判断、决策简报和增长机会。
- `phase2_models.py`、`phase2_catalogs.py`、`phase2_storage.py`：领域契约、规则目录、派生对象与任务状态。
- `crossborder_api/runtime.py`：Overview、Topic、Data Hub、Agent 与导出的 Web 数据适配层；当前体积较大，是后续拆分重点。
- `crossborder_api/main.py`：FastAPI 路由、CSV 导出和静态前端入口。
- `frontend/src/pages/OverviewPage.tsx`：经营总览；`AnalyticsPage.tsx`：五主题分析；`DataHubPage.tsx`：数据中心；`AiAnalystPage.tsx`：AI 分析师。

## 5. Important Decisions

Decision: 原始业务数据始终只读，标准化、类型转换、汉化和币种换算只生成分析或展示副本。

Reason: 商业分析必须可追溯，页面和报告不能静默改变源事实。

Date: 2026-07-16

Decision: SQL 是正式事实来源；Python 负责业务推导；只开放注册指标和参数化查询，不向页面或 Agent 开放任意 SQL。

Reason: 先稳定数据版本、查询口径和证据血缘，避免指标漂移与权限绕过。

Date: 2026-07-19

Decision: 分析状态与人工任务状态分离；任务完成、驳回或等待补数不得改写历史异常和诊断事实。

Reason: 分析事实需要可审计，人工处置又必须能独立流转和复盘。

Date: 2026-07-19

Decision: 不完整周期不参与环比、异常优先级和确定性经营判断；比较必须使用页面明确展示的完整、等长周期。

Reason: 未完成月份与完整基期不可公平比较，会制造趋势断崖和假异常。

Date: 2026-07-21

Decision: 经营总览每个模块公开判断口径、比较周期和阈值；经营洞察独立分析可持续性、保护指标和历史复现，不重复待办事项。

Reason: 用户必须能复现筛选逻辑，并从洞察获得待办列表之外的判断价值。

Date: 2026-07-21

Decision: 专题分析采用决策优先的信息板；先呈现趋势、异常、发现、驱动、证据和动作，再提供构成、排行和明细下钻。

Reason: 运营人员首先需要判断是否行动，通用 KPI 加独立 AI 侧栏会打断经营阅读顺序。

Date: 2026-07-21

Decision: 日期、市场和品类属于分析筛选并同步 URL；搜索、分页和每页数量只属于明细交互。

Reason: 搜索或翻页不能隐式改变 KPI、趋势、排行、证据和报告口径。

Date: 2026-07-21

Decision: 业务结论、异常对象、影响额和驱动因素由后端真实数据生成，前端不使用随机数据、Mock、Placeholder 或模板结论。

Reason: 判断逻辑必须可测试、可追溯，并被所有页面和报告一致消费。

Date: 2026-07-21

## 6. AI Development Rules

修改代码时：

先读取用户指定阶段、参考设计、现有契约和真实数据流；确认允许修改的页面与禁止范围。让仓库现有模式决定实现方式，不以通用后台模板替代产品要求。

必须：

- 使用中文业务语言；缩写首次出现时说明含义；避免“AI 洞察”等空泛系统语言。
- 保持全局导航、数据中心正文和 Design System 稳定，除非任务明确允许修改。
- 严格遵守阶段范围；用户禁止修改 Overview、Topic 或 AI 分析师时，不顺手重构对应页面。
- 所有 KPI、趋势、异常、机会、证据和动作来自真实筛选后数据；展示周期、比较周期、公式、阈值或判断依据。
- 使用完整可比较周期；数据不足时明确降级，不回退为看似确定的结论。
- 区分数学贡献、相关关系和已验证原因；缺少广告、库存、活动、价格等数据时只提出核查方向。
- 所有“查看、详情、导出、报告、筛选、分页”入口实现真实交互，并让按钮文字与实际行为一致。
- 保留设计稿已有模块；新增抽象必须消除真实复杂度或匹配既有模式。

不要：

- 不要使用 Mock、随机数据、Placeholder、可见 TODO 或重复模板文案补齐页面。
- 不要删除设计稿模块，不要把经营洞察改成待办事项的重复展示。
- 不要混用月度、周度、部分周期或不同基期而不注明。
- 不要让前端根据展示数据临时猜异常、原因和建议。
- 不要把退货关联 GMV 写成实际退款损失，不要把贡献写成确定因果。
- 不要在真实业务验证、回归、性能和提交收口之前继续增加装饰性图表或智能能力。

测试要求：

- 后端测试覆盖五主题独立指标、趋势、异常、驱动、明细、筛选影响范围、分页搜索和 CSV 导出。
- 前端至少运行 TypeScript 构建与 Vitest；交互改动使用 Playwright 实测 Drawer、报告、筛选、导出和按钮语义。
- 页面在桌面和 393px 移动视口检查水平溢出、文字裁切、固定头部、图表非空和卡片比例；必要时保存截图对照参考设计。
- 修改共享分析口径或底座时运行完整 CrossBorder 回归，并按依赖范围验证 AutoClean。

文档要求：

- 稳定产品状态、架构、规则和决策更新本文件；每日推进、阻碍和 Tomorrow Top 3 写入 `docs/founder-log/`。
- 发布时同步 README、CHANGELOG、OpenAPI 类型、测试结果和迁移说明。

## 7. Known Risks

当前风险：

工作区包含大量跨阶段、未提交或未跟踪改动，且 React/FastAPI 新产品与旧 Streamlit 兼容链路并存。未来操作必须保留现状，按产品边界拆分提交，不能用清理命令覆盖用户工作。

技术风险：

专题请求仍可能需要十余秒；`runtime.py` 同时承担多个页面适配，职责和体积偏大；前端生产包约 1.65 MB，尚未代码分割；OpenAPI 生成类型与页面 DTO 可能漂移；短日期范围不足两个完整周期时的降级仍需强化；CI、跨平台安装和自动性能门槛尚未建立。

产品风险：

当前样例假设一行一订单，缺少真实退款、成本、库存、广告、活动、价格事件、退货原因和物流节点。Top5“异常对象”可能同时包含不利变化和明显改善，需要继续校准命名与阈值；五主题自然语言和建议尚未经过真实运营人员逐项验收。

商业风险：

真实团队的持续使用、任务完成率、建议带来的量化收益、付费意愿和数据接入成本仍未知。当前验证证明用户重视口径透明和决策顺序，但尚未证明产品能持续改善真实经营结果。
