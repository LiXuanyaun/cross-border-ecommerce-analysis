# CrossBorder v4.1 数据一致性与完整功能验收 PRD

**状态：** 待实施

**基线：** v4.0.0

**目标：** 先消除“改完一个功能，下一步使用才暴露问题”的系统性回归，再继续增加业务能力。

本 PRD 遵循 [AI 产品 PRD 编写规范 v3.0](AI_PRODUCT_PRD_STANDARD_V3.0.md)。它补充并取代旧 PRD 中较弱的测试验收表述，不改变已经确认的产品定位和业务边界。

## 1. 问题定义

当前项目的单个模块测试能够通过，但完整用户流程仍可能出现：

- 同一份 AdventureWorks 订单生成两个数据集编号。
- 数据中心出现两个同名数据集。
- 普通 Dashboard 有订单，广告、退款和物流页面却找不到对应数据。
- 原始订单与模拟扩展在不同页面给出容易误解的结果。
- 维护清理可能保留错误副本并破坏多业务关联。

这些问题的共同原因是：导入、分析、页面、报告、Agent 和维护分别验证，没有把它们作为同一条用户流程验收。

### 当前证据

- 当前数据库存在两份来源哈希相同、各 60,398 行的 AdventureWorks 订单。
- 数据中心接口同时返回两个同名 AdventureWorks 数据集。
- 多业务接口只识别其中一个数据集。
- 现有多业务测试可以全部通过，但没有检查普通分析后数据集数量是否保持不变。
- 浏览器回归主要检查页面打开、布局和图表非空，没有完成导入到重启的完整流程。

## 2. 本版本目标

v4.1 只解决可靠性和一致性，不扩展新的业务模块。

必须达到：

1. 一份源数据只有一个正式数据集身份。
2. 用户始终知道当前页面使用哪份数据。
3. 普通订单分析与模拟业务分析不会被表述成同一种真实事实。
4. 页面、报告、任务和 Agent 使用相同数据范围。
5. 重启、重复导入、升级和维护后结果仍然正确。
6. 完整用户流程进入自动化发布门禁。

### 目标用户与价值

主要用户是使用 CrossBorder 完成经营复盘的跨境电商经营者和运营负责人。

用户价值：用户选择一份数据后，可以确信所有页面、报告和 Agent 都在解释同一份数据，不需要自行判断结果是否混算或失效。

业务价值：减少试点中的错误结论和重复返工，让“产品可稳定使用”先于继续堆叠功能。

### 成功指标

|类型|指标|目标|
|---|---|---|
|首要指标|P0 完整用户流程通过率|100%|
|数据指标|同一来源的正式数据集数量|1|
|一致性指标|页面、报告和 Agent 范围一致率|100%|
|完整性指标|外键错误和孤立业务事实|0|
|回归指标|全新数据库和历史数据库验收|全部通过|
|发布护栏|被跳过的 P0 测试|0|

## 3. 不在本版本范围

- 新增库存、店铺、活动或渠道数据。
- 扩大 Agent 自主执行权限。
- 新增预测模型。
- 重新设计全部页面视觉。
- 把模拟广告、退款和物流表述为真实经营数据。

## 4. 强制数据规则

### 4.1 数据集隔离

- `ecommerce_sales_34500.csv` 与 AdventureWorks 必须是独立数据集。
- 页面和查询必须使用明确的 `dataset_id`，不得跨数据集聚合。
- 同一源文件、同一版本、同一导入契约重复导入时必须复用原 `dataset_id`。
- 打开 Dashboard、生成报告或调用 Agent 不得创建新的数据集。

### 4.2 AdventureWorks 数据边界

- 销售订单、商品、客户、金额、成本、订单日期、发货日期和运费来自 AdventureWorks。
- 广告、退款、承运商、实际配送和物流轨迹来自 `synthetic_extension` 模拟扩展。
- 普通 Dashboard 只使用 AdventureWorks 原始订单事实。
- 多业务专题可以关联模拟扩展，但页面、报告和 Agent 必须持续显示“模拟数据”。
- 原始订单没有真实退货记录时，普通 Dashboard 应显示“真实退货数据不可用”，不得显示为“退货率为 0”。
- `OrderDate -> ShipDate` 只能称为出库或发货准备时长，不得称为真实配送时长。
- 模拟 `ShipDate -> ActualDeliveryDate` 可以称为运输时长，但必须标注模拟来源。

### 4.3 标识一致性

一次用户分析中的以下内容必须保持一致：

- `dataset_id`
- `scope_id`
- 分析周期
- 币种
- 质量状态
- 模拟数据标识
- 指标版本和证据编号

## 5. 当前 P0 缺陷

|编号|缺陷|通过标准|
|---|---|---|
|D01|AdventureWorks 订单被保存为两个数据集|只保留一个正式身份，重复分析不再创建新身份|
|D02|数据中心显示两个同名 AdventureWorks|只显示一个可选择的数据集|
|D03|普通 Dashboard 与退款专题语义冲突|普通页显示真实字段不可用，专题页明确显示模拟结果|
|D04|去重清理可能删除带扩展关联的订单副本|维护前识别完整数据集，维护后无孤立事实和外键错误|
|D05|现有测试没有覆盖导入后的完整用户流程|P0 流程进入浏览器和持久状态回归|

## 6. 完整功能验收流程

### E2E-01 默认演示数据启动

- **用户步骤：** 启动产品并打开经营总览。
- **预期结果：** 明确显示正在使用“全量经营演示数据”，指标来自 34,500 行样例。
- **禁止结果：** 自动混入 AdventureWorks 或历史上传数据。

### E2E-02 首次导入 AdventureWorks

- **用户步骤：** 在数据中心预检并确认导入 AdventureWorks 目录。
- **预期结果：** 生成一个正式 `dataset_id`；订单和扩展表共享该身份；来源和模拟标识清晰。
- **数据检查：** 源文件行数、文件哈希、订单行、业务事实和关联率与导入清单一致。
- **禁止结果：** 部分写入、两个数据集身份或未标识模拟数据。

### E2E-03 导入后打开 Dashboard

- **用户步骤：** 导入完成后选择 AdventureWorks，依次打开总览、专题分析和数据中心。
- **预期结果：** 三个页面保持同一 `dataset_id`；数据中心仍只有一份 AdventureWorks。
- **禁止结果：** 打开分析页面后数据库新增第二份订单。

### E2E-04 普通分析与多业务分析

- **用户步骤：** 查看经营、商品、客户、广告、退款和物流页面。
- **预期结果：** 普通分析使用原始订单；多业务分析使用带明确标识的模拟扩展；来源说明始终可见。
- **禁止结果：** 把缺少真实退货解释成退货率为 0，或把模拟退款解释成真实损失。

### E2E-05 报告与 Agent 一致性

- **用户步骤：** 在同一数据集和周期生成报告，并向 Agent 询问当前异常。
- **预期结果：** 页面、报告和 Agent 的 `dataset_id`、周期、指标、模拟标识和限制一致。
- **禁止结果：** Agent 或报告遗漏模拟限制，或者引用另一个数据集。

### E2E-06 刷新与重启

- **用户步骤：** 选择 AdventureWorks，刷新页面，停止并重新启动服务。
- **预期结果：** 数据集身份不变化；数据库不新增订单副本；持久化状态符合 demo/private 模式定义。
- **禁止结果：** 每次启动或首次分析都生成新数据集。

### E2E-07 重复导入

- **用户步骤：** 再次导入完全相同的 AdventureWorks 目录。
- **预期结果：** 返回原 `dataset_id`，订单和业务事实行数不增加，导入结果标识为复用。
- **禁止结果：** 重复订单、重复扩展事实或新数据集身份。

### E2E-08 维护与清理

- **用户步骤：** 在数据库副本上执行维护清理。
- **预期结果：** 保留包含完整订单和业务扩展的正式数据集；清理后所有页面和报告可用。
- **数据检查：** SQLite 外键检查为 0；没有孤立的导入批次、订单映射、退款、物流或广告归因。
- **禁止结果：** 仅按创建时间保留不完整副本，或清理后业务页面失效。

### E2E-09 v4.0 历史数据库升级

- **用户步骤：** 使用脱敏的 v4.0 历史数据库副本启动 v4.1。
- **预期结果：** 迁移可重复运行；已有数据、任务和报告范围不丢失；重复 AdventureWorks 身份被安全合并。
- **禁止结果：** 静默删除、重复写入、口径改变或无法回滚。

### E2E-10 失败与恢复

- **用户步骤：** 分别制造缺文件、错误关联、写入中断和无效金额。
- **预期结果：** 导入阻断并说明具体原因；数据库没有半成品事实；修复后可以重新导入。
- **禁止结果：** 订单已写入但业务扩展处于不可识别的半完成状态。

### E2E-11 桌面与窄屏真实交互

- **用户步骤：** 在桌面和 393px 宽度完成数据选择、筛选、详情、报告和返回。
- **预期结果：** 不仅页面可打开，所有关键操作可以完成，文本和控件不重叠。
- **禁止结果：** 只检查标题、截图或图表非空就判定流程通过。

## 7. 自动化测试分层

|层级|本项目必须覆盖|
|---|---|
|单元测试|数据集身份生成、指标公式、模拟标识和清理选择规则|
|数据契约测试|AdventureWorks 粒度、关联键、币种、来源和扩展字段|
|集成测试|导入 -> 持久化 -> 普通分析 -> 多业务分析 -> 报告 -> Agent|
|API 契约测试|所有响应保留数据集、范围、质量和模拟标识|
|浏览器端到端|真实点击 E2E-01 至 E2E-05 和 E2E-11|
|持久状态回归|E2E-06 至 E2E-10，分别使用全新数据库和历史数据库|
|性能测试|10 万行导入、分析、筛选、报告和数据库增长|

## 8. CI 与发布门禁

每次涉及数据、分析、报告、Agent 或维护的变更必须通过：

1. 后端完整回归。
2. 前端测试与构建。
3. 全新数据库完整流程。
4. v4.0 历史数据库升级流程。
5. 桌面和 393px 浏览器完整操作。
6. 页面、报告和 Agent 一致性对账。
7. SQLite 外键和重复数据检查。
8. 10 万行性能门禁。

以下情况禁止发布：

- 任一 P0 流程失败或被跳过。
- 只验证页面打开，没有验证用户操作。
- 只使用临时空数据库。
- 同一来源出现多个正式数据集身份。
- 模拟数据和原始数据没有清晰区分。
- 维护操作没有在数据库副本上验证。
- 本次未记录实际运行和未运行的检查。

## 9. 开发顺序

### Phase 1：身份与数据修复

- 统一 `dataset_id` 的唯一生成和传递规则。
- 阻止分析、报告和 Agent 重新持久化同一数据。
- 增加重复身份回归测试。
- 设计可回滚的现有重复数据修复。

🔶 **假设：** 当前带完整多业务关联的 `adventureworks-...` 身份应作为合并后的正式身份。实施前必须通过引用关系和报告、任务使用情况再次确认，不能只按创建时间决定。

### Phase 2：语义和页面一致性

- Dashboard 明确当前数据来源。
- 分开“真实不可用”和“模拟结果”。
- 统一页面、报告和 Agent 的范围与限制。

### Phase 3：长期状态和发布门禁

- 增加重启、重复导入、升级和维护测试。
- 将真实浏览器用户流程纳入 CI 或发布前强制验收。
- 形成每次发布的验收证据清单。

## 10. 依赖与风险

### 依赖

- 必须先创建当前 `ecommerce.db` 的可恢复副本，才能执行重复数据修复。
- 必须准备一个脱敏、版本固定的 v4.0 历史数据库测试样本。
- 必须能够在浏览器自动化中完成真实数据选择和跨页面操作。

### 风险与缓解

|风险|影响|缓解措施|
|---|---|---|
|错误删除带扩展关联的数据集|退款、物流和报告失效|先做只读引用审计，在副本迁移并验证后再处理正式库|
|只修当前数据库、不修身份生成|下次分析再次重复|先修身份规则和回归测试，再迁移历史数据|
|测试仍只使用空数据库|升级问题继续漏检|CI 同时运行全新库和历史库两条路径|
|模拟与真实语义继续共用标签|用户误判经营结果|将来源和不可用状态写入后端契约，不由前端猜测|
|完整流程测试过慢而被跳过|发布门禁失效|P0 流程保持精简，慢测试单独运行但不允许跳过发布|

## 12. PRD 自评

**最强部分：** 数据身份、模拟数据边界和完整用户流程已有当前数据库与代码证据，可以直接转成测试。

**最弱部分：** 历史数据合并策略尚未确定，特别是报告、任务和分析结果如何重绑，不能在实现时临时决定。

**最高风险假设：** 保留带多业务扩展的旧身份不会破坏其他已保存对象。必须先用只读查询验证全部引用。

**建议的下一步：** 先确认数据集合并规则和回滚方案，再实施 Phase 1；在这两个决定完成前不执行现有自动去重。

## 13. Definition of Done

v4.1 只有同时满足以下条件才算完成：

- [ ] 当前已知的重复 AdventureWorks 身份得到可回滚修复。
- [ ] 重新导入和打开 Dashboard 不再创建新身份。
- [ ] 原始订单与模拟扩展在所有输出中清晰区分。
- [ ] 页面、报告、任务和 Agent 范围一致。
- [ ] 全新数据库和历史数据库均通过完整流程。
- [ ] 重启、失败重试和维护后数据仍完整。
- [ ] E2E-01 至 E2E-11 全部通过且无关键跳过。
- [ ] 测试记录明确列出实际运行项和未运行项。
- [ ] 在本 PRD 完成前不新增业务模块。
