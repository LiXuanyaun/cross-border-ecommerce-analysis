# Founder Daily Review

日期：2026-07-22

项目：CrossBorder AI Analytics

---

# 1. 今日一句话总结

AI 分析师从“像固定模板的对话页”推进为能展示本轮问题、回答、工具轨迹和证据摘要的可验证分析界面。

---

# 2. 今日项目推进

## 产品能力变化

昨天：AI 分析师已经接入受控工具、会话和 SSE 结果流，但页面第一屏仍以固定 KPI 仪表盘为主，用户发不同问题时看不出右侧结果区随本轮对话变化，容易被判断为假逻辑。

今天：AI 分析师结果区改为回答优先，展示当前问题、当前回答、工具数量、证据数量、执行计划、工具观察和证据摘要；对话栏和长回答增加固定高度与内部滚动；常规桌面宽度恢复左右分栏。

现在：用户可以直接看到“这一次问了什么、AI 回了什么、调用了哪些工具、证据来自哪里”，对话体验不再无限拉长页面，也不再像固定展示板。

---

## 用户价值变化

这次改动降低了用户对 Agent 真实性的怀疑。AI 分析师不只是返回一段话，而是把回答、计划、工具状态和证据放在同一轮上下文里，方便运营人员判断回答是否基于真实数据、是否有证据支撑、哪些能力因为数据不足被跳过。

---

# 3. 今日关键决策

Decision: AI 分析师页面必须以本轮问答和工具证据为中心，KPI、趋势和 Top Impact 只能作为指标上下文，不能抢占第一屏。

Reason: 对话型产品的信任首先来自“我的问题改变了系统输出”，如果结果区长期显示固定仪表盘，即使后端有真实接口，用户也会认为功能是假的。

Alternatives: 继续保留 KPI 仪表盘作为概览第一屏，或只在左侧聊天气泡展示回答。

Impact: Agent 页面更接近可试点产品体验；代价是前端需要持续消费 `agent_plan`、`tool_observations`、状态和证据，而不能只展示通用 dashboard。

---

# 4. 当前项目状态

## 产品

当前能力：经营总览、专题分析、数据中心、任务、报告和 AI 分析师已形成更完整的试点级闭环；Agent 页面已经能展示真实问答上下文、工具调用轨迹和证据摘要。

下一阶段：用真实运营问题连续追问 Agent，检验回答是否真正受问题、历史对话、scope 和工具结果影响，而不是只靠确定性模板兜底。

## 技术

当前状态：前端 build、Vitest 和浏览器回归通过；AI 分析师页面已验证左右分栏、内部滚动和本轮结果展示。私有模式后端可运行，CC Switch 导入入口可用，但 provider 是否已配置仍取决于用户在网页端完成导入。

技术风险：`runtime.py` 仍偏大；SQLite 数据库体积和快照/缓存增长压力仍在；100k 基准上一次仍高于 15 秒门槛，当前分数不应沿用旧评估，需要重新完整跑性能与容量评测后再定。

## 商业

已经验证：用户对“真逻辑”和“可见证据链”极敏感，静态感会直接损害产品可信度；Agent 页面必须把可验证过程展示出来。

未知问题：真实商家数据接入后，成本、退款、广告、库存、活动、物流原因等变量缺失仍会限制归因深度；成熟 Agent 的规划、试错、反思和评测尚未完成。

---

# 5. 今日最大阻碍

问题：AI 分析师页面虽然有真实接口，但结果展示没有把本轮问题和回答放在中心，且对话栏会随内容延伸。

影响：用户会把“展示层固定”理解为“Agent 逻辑被删掉或是假逻辑”，这比普通 UI 瑕疵更伤信任。

已经尝试：修复结果区信息架构、工具状态展示、证据摘要、对话高度和桌面分栏，并通过构建、单测、浏览器回归和真实页面发问检查。

下一步：继续验证后端回答是否足够跟随问题变化；如果模型未配置或模型失败，确定性兜底也要更明确地解释问题边界和调用结果。

---

# 6. Tomorrow Top 3

1. 重新完整评估当前版本分数，重点复跑 100k 性能、数据库容量和 Agent 真实问答差异。
2. 优化 100k SQLite 流水线和快照/缓存容量治理，把硬门槛和增长压力继续压下去。
3. 推进 Agent 从受控工具观察升级为更完整的 planner-executor：问题理解、工具选择、追问上下文、失败降级和评测用例。
