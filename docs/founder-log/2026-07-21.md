# 2. 今日项目推进

## 产品能力变化

昨天：页面已经具备 KPI、趋势、排行、明细和分析建议，但判断标准分散，洞察与待办容易重复，专题分析的结论、证据和动作被拆在不同区域，用户需要自己拼接经营含义。

今天：经营总览为各模块公开判断口径、比较周期和阈值，增长机会使用完整周期和确定性门槛，经营洞察增加可持续性与历史复现分析；专题分析按“趋势对比—异常对象—关键发现—驱动因素—数据证据—建议动作”重组，五个主题分别使用真实数据计算，并保留筛选、下钻、搜索、分页、导出和完整报告。

现在：运营人员可以先看到本期发生了什么、哪些对象影响最大、为什么需要关注、证据是什么和下一步做什么，再进入构成、排名与明细核查，不必猜测系统的筛选逻辑或在多个模块之间拼结论。

---

## 用户价值变化

用户开始能够复算系统判断，并区分经营事实、驱动贡献和建议动作。统一完整周期减少假异常，直接的业务语言降低理解成本，完整对象入口和明细下钻让结论可以被核查、交接和执行。

---

# 3. 今日关键决策

Decision: 将专题分析设计为决策优先的信息板，所有结论由后端真实数据生成；同屏比较只使用完整、等长周期，并公开口径，不让前端临时拼装结论。

Reason: 用户首先要判断是否值得行动，而不是浏览更多图表；混用未完整月份、不同周期或不公开阈值会直接损害对系统逻辑的信任。

Alternatives: 保留 KPI、图表和独立 AI 侧栏的通用后台布局，或由前端根据排行和趋势临时生成自然语言摘要。

Impact: 页面更接近真实经营复盘顺序，五个主题拥有独立结论和明细，分析口径可追溯；代价是接口承担更多比较和解释逻辑，后续必须持续用测试约束周期、占比和语言准确性。

# 4. 当前项目状态

## 产品

下一阶段：对五个专题逐一进行真实经营案例验收，校准异常排序、动作可执行性和文案边界，再决定是否进入下一页面阶段。

## 技术

当前状态：专题判断由 FastAPI 统一计算，React 只负责展示和交互；不完整月份被排除，URL 筛选会重算整张判断板，搜索和分页只影响明细。本次 12 项 API 测试、3 项前端测试、生产构建和桌面/移动浏览器交互检查通过。

技术风险：当前工作区仍有大量跨阶段未提交改动；完整项目回归、性能基线、OpenAPI 类型同步和构建包体积治理尚未在本次验收中完成。

## 商业

已经验证：用户明确重视判断口径、周期一致性、自然业务语言和决策顺序，单纯增加图表或 AI 文案不足以建立产品信任。

未知问题：当前仍使用项目内演示订单数据，异常门槛和建议动作是否适合真实商家、是否能提高处置效率或经营结果，尚未经过真实运营周期验证。

# 5. 今日最大阻碍

问题：视觉验收时发现筛选结束日期为 09/11，系统曾把未完整的 9 月与完整月份比较，制造出趋势断崖和 -62.3% 的假异常。

影响：即使页面高度还原设计稿，错误的周期逻辑仍会让用户立即怀疑整套分析，视觉完成不能替代数据可信。

已经尝试：通过真实浏览器截图核对曲线与 KPI，追溯比较周期，统一排除筛选范围首尾的不完整月份，并重新验证趋势、占比、移动端布局和详情入口。

下一步：为任意日期范围、跨月边界和不足两个完整周期增加更系统的测试，并在页面继续明确显示本期与上期范围。
