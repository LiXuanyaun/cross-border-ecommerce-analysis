# CrossBorder AI Analytics 统一数据集与专题体验修正 PRD

**文档版本：** 1.0  
**日期：** 2026-07-31  
**产品基线：** 已完成核心恢复后的 React + FastAPI 主产品  
**状态：** 需求已确认，可进入实施  
**需求范围：** `demo-all` 与 AdventureWorks 合并、客户专题正常状态、多业务展示精简、旧派生数据清理

## 0. 执行摘要

本次需求不是继续修改核心恢复方案，而是在现有可用产品上新增一条独立的数据与体验改进链路。系统需要将 `demo-all` 与 AdventureWorks 整合为一个新的、版本化的统一数据集，让用户只选择一次数据即可使用经营总览、普通专题、多业务专题、报告、任务和 Agent；同时修复客户专题“有明细、有 KPI，但异常、驱动、证据和建议为空”的误导性体验，并将广告、退款、物流页面中无决策价值的技术关键字下沉到数据说明。

合并不等于直接拼接。两份来源必须先经过订单粒度、业务键、币种、日期语义、金额口径和质量校验；只有口径兼容的事实才可汇总。确定性重复订单行只计入一次，冲突时优先采用 AdventureWorks 记录。两份原始数据保持只读，所有来源、去重、冲突和模拟扩展状态必须可追溯。旧派生数据只在统一数据集通过验收后停用，并经过 7 天回滚窗口后再物理清理。

## 1. 核心定义

### 1.1 一句话定义

统一数据集与专题体验修正是一项面向跨境电商运营人员的数据产品升级，通过可审计地合并 `demo-all` 与 AdventureWorks，并统一普通专题和多业务专题的业务表达，使用户用一份数据完成全部分析且不会把正常状态、演示数据或技术字段误认为业务问题。

### 1.2 产品定位

本次负责：

- 新建一个由 `demo-all` 与 AdventureWorks 派生的统一数据集。
- 使用确定性业务键去重，并提供来源、冲突和金额审计。
- 让一个统一 `dataset_id` 覆盖经营总览、普通专题、多业务专题、报告、任务和 Agent。
- 修复客户专题无异常时分析区域全部为空的问题。
- 将多业务页面调整为结论、对象、影响、证据和动作优先。
- 清理不再参与产品运行的旧 scope、缓存、暂存记录和重复索引。
- 保留原始文件、来源身份、质量状态和模拟状态。

本次不负责：

- 修改或删除 `demo-all` 与 AdventureWorks 原始文件。
- 在币种、粒度或金额口径不一致时强行汇总。
- 用模糊相似度猜测两条订单是否重复。
- 为填满页面伪造异常、驱动、财务损失或确定性因果。
- 将 AdventureWorks 或 `demo-all` 包装成客户真实经营数据。
- 新增成本、库存、活动、店铺、渠道或实时数据库同步。
- 重做已经完成的核心恢复、导入容量、AI Markdown 或启动链路。

### 1.3 设计原则

1. 原始数据只读，合并结果创建新版本。
2. 统一入口不等于盲目相加，先校验口径再汇总。
3. SQL 与注册指标继续作为正式事实层，前端不发明结论。
4. 正常状态也是有效分析结果，没有异常时不得制造异常。
5. 首屏使用业务语言，技术血缘按需展开。
6. 示例、模拟和数据不足状态必须持续披露。
7. 删除前先预览、停用和验证，物理清理必须可审计。

## 2. 商业目标

### 2.1 商业问题

| 商业问题 | 用户影响 | 产品影响 |
|---|---|---|
| 普通专题与多业务能力依赖不同数据集 | 用户需要反复切换，无法形成同一经营视图 | 报告、任务和 Agent 容易出现数据身份分叉 |
| 客户专题有 5,350 条明细和 4 个 KPI，但异常、驱动、证据和动作均为空 | 用户误以为客户数据没有加载 | 正常经营状态无法转化为可理解的复盘结果 |
| 多业务首屏展示内部 ID、原始字段名和模拟实现关键字 | 客户需要理解技术结构才能看懂页面 | 降低交付完成度和业务可信度 |
| 旧数据集、scope 和缓存持续存在 | 用户难以判断哪份数据仍然有效 | 增加误选、旧缓存和维护成本 |
| 两份数据直接拼接可能重复计数 | 订单数、GMV 和客户贡献被放大 | 产生错误经营判断 |

### 2.2 成功指标

| 目标 | 当前状态 | 验收目标 |
|---|---|---|
| 单数据集覆盖 | 功能分散在 `demo-all` 与 AdventureWorks | 统一数据集覆盖产品功能矩阵的 100% |
| 合并可复算 | 尚无正式跨源合并审计 | 输入、保留、去重、冲突、隔离和输出金额全部可复算，差异为 0 |
| 杜绝重复计数 | 跨源重复情况待预演 | 同一确定性订单行业务键在统一事实层最多出现 1 次 |
| 客户分析完整 | 无异常时四类分析内容均为空 | 正常状态、关键发现、分群贡献、证据和监测动作均有明确结果或明确降级 |
| 多业务可读 | 首屏存在技术关键字和低价值内容 | 首屏内部 ID、规则号、查询名、原始字段名和 `synthetic_extension` 出现数为 0 |
| 来源透明 | 示例与模拟状态容易混淆 | 页面、报告、任务和 Agent 的来源、周期、币种、质量和模拟状态一致率 100% |
| 清理安全 | 旧派生数据尚未精确盘点 | 原始文件误删为 0；停用后 7 天内可恢复；最终删除目标审计率 100% |
| 性能不回退 | 核心恢复已完成性能优化 | 统一数据集继续满足现有首屏、专题切换和详情展开性能门槛 |

### 2.3 商业结果边界

- 本次衡量的是数据可信度、功能覆盖和分析可理解性，不以增加异常数量为成功。
- AdventureWorks 与 `demo-all` 均属于示例性质的数据来源，不能据此宣称客户真实收入、利润或损失。
- 🔶 **假设：** 一份数据覆盖全部功能后，客户演示和试点验收的操作成本会下降；真实用户效率提升仍需试点验证。

## 3. 用户场景

### 3.1 主要用户

| 维度 | 内容 |
|---|---|
| 用户 | 跨境电商运营负责人、经营分析人员、产品演示与交付人员 |
| 时间 | 周期复盘、客户演示、数据验收或问题排查时 |
| 任务 | 使用同一份数据查看全部业务专题并复核结论 |
| 痛点 | 数据集切换、空白分析区和技术字段干扰判断 |
| 期望结果 | 一次选数完成全部分析，结论有业务含义且可追溯 |

### 3.2 核心场景

| 场景 | 用户动作 | 期望结果 |
|---|---|---|
| 首次进入产品 | 选择统一数据集 | 所有页面继承同一数据身份，不再切换来源 |
| 客户专题复盘 | 查看未命中异常的客户范围 | 明确看到“未发现异常”，并获得结构、趋势、分群证据和监测动作 |
| 多业务复盘 | 查看广告、退款和物流 | 首屏直接回答发生了什么、影响谁、证据是什么、下一步做什么 |
| 来源核验 | 展开数据说明 | 查看两份来源占比、周期、币种、质量和模拟限制 |
| 数据维护 | 清理不再使用的数据 | 先看到精确清单和引用，停用可回滚，原始文件不受影响 |

### 3.3 Jobs-to-be-Done

- 功能任务：用一份可追溯数据完成全部经营分析。
- 情绪任务：确信页面不是空白、旧缓存或重复数据造成的假结果。
- 协作任务：向客户或管理者解释结论时不需要讲解内部字段和实现术语。

## 4. 输入数据

### 4.1 数据来源

| 来源 | 当前用途 | 合并后的定位 |
|---|---|---|
| `demo-all` | 普通经营与客户等专题的演示数据 | 统一数据集的示例来源之一 |
| AdventureWorks | 订单、普通专题和广告/退款/物流多业务演示 | 统一数据集的示例来源之一；确定性冲突时优先 |
| AdventureWorks 多业务扩展 | 广告、退款和物流功能验证 | 标记为“演示推算数据”，不得伪装为真实业务事实 |

### 4.2 最低标准字段

| 标准字段 | 类型 | 用途 | 缺失行为 |
|---|---|---|---|
| `order_id` | string | 订单身份 | 阻断该记录进入订单事实 |
| `order_line_id` 或可确定的行号 | string | 订单行身份与跨源去重 | 无法确定时不做跨源自动去重 |
| `order_date` | date | 周期、趋势和比较 | 阻断周期结论 |
| `total_amount` | number | GMV、客单价和贡献 | 阻断金额结论 |
| `currency` 或明确批次币种 | string | 金额可比性 | 不明确时禁止跨源金额汇总 |
| `customer_id` | string | 客户规模、分群和频次 | 客户专题显式降级 |
| `product_id` | string | 商品专题 | 商品专题显式降级 |
| 市场字段 | string | 市场专题 | 市场专题显式降级 |
| 广告、退款、物流字段 | domain-specific | 多业务专题 | 使用真实字段、演示推算或数据不足三级状态 |

### 4.3 统一事实附加字段

- `source_dataset`：记录来自 `demo-all` 还是 AdventureWorks。
- `source_record_key`：保留来源记录身份。
- `canonical_order_line_key`：确定性标准订单行业务键。
- `source_state`：示例源数据、演示推算数据或未来真实导入数据。
- `merge_version`：统一数据集规则与版本。
- `quality_state`：可汇总、来源隔离或数据不足。

### 4.4 合并前检查

- 统计两份来源的行数、订单数、订单行粒度、客户数、日期范围、币种和金额。
- 检查订单号与订单行号在两份来源中的语义是否一致。
- 检查金额是否含税、是否包含运费、是否存在负数或退款混入。
- 生成只读合并预演，列出保留、重复、冲突和隔离记录。
- 任何未确认项必须标记为开放检查，不得由实现者自行假设为一致。

## 5. 核心功能

### 5.1 新建统一数据集

**目标：** 在不改写两份来源的前提下生成一个新的、版本化的统一 `dataset_id`。

**流程：**

1. 分别读取并标准化 `demo-all` 与 AdventureWorks。
2. 验证业务键、粒度、币种、日期和金额口径。
3. 对可确定的跨源订单行执行去重。
4. 同一业务键值冲突时采用 AdventureWorks，并记录被排除的 `demo-all` 值。
5. 非重复且通过契约的记录全部保留。
6. 不兼容记录进入来源隔离区，不进入统一汇总。
7. 原子提交统一数据集、来源映射和合并审计。

### 5.2 一份数据覆盖全部功能

以下消费者必须使用同一统一数据集、scope、周期、币种、质量和来源状态：

- 经营总览。
- 销售、客户、商品和市场普通专题。
- 广告、退款和物流多业务专题。
- 报告、任务和 Agent。
- 数据证据和来源说明。

private 产品在统一数据集验收后只展示这一份业务数据入口。原来源保留在维护和审计层，不出现在普通选择列表。

### 5.3 客户专题正常状态修复

**目标：** 区分“没有异常”和“没有数据”，并在没有异常时继续提供经营价值。

**要求：**

- 异常对象显示“当前范围未发现符合规则的客户异常”。
- 关键发现展示客户规模、价值分群和趋势变化。
- 驱动因素展示 VIP、高价值、流失风险等分群的贡献或构成，不表述为因果。
- 数据证据展示客户数、人均贡献、购买频次、周期、币种、样本范围和限制。
- 建议动作改为保持、监测或复核策略，并写明触发复查的指标条件。
- 字段不足时显示“数据不足”和所缺字段，不用模板内容填满页面。
- 正式异常规则命中时仍使用原异常、诊断、证据和建议链路。

### 5.4 多业务展示精简

**对齐目标：** 广告、退款和物流与普通专题采用同一信息顺序：KPI、趋势、异常对象、关键发现、驱动因素、业务证据、建议动作和必要明细。

**首屏保留：**

- 业务指标与趋势。
- 需要关注的对象和影响。
- 有口径的关键发现与贡献结构。
- 可展开的证据和建议动作。
- 简短但持续可见的“演示推算数据”状态。

**首屏移除或下沉：**

- `dataset_id`、`scope_id`、规则编号、查询名和摘要哈希。
- `synthetic_extension`、原始英文字段名和调试状态。
- 重复说明、空卡片、无业务含义的关键字标签。
- 不支持识别对象、理解影响或采取动作的默认明细列。

技术血缘、完整字段、规则版本和来源记录键进入可展开的“数据说明”或证据详情。

### 5.5 旧派生数据清理

**可清理对象：** 已被统一数据集替代且没有有效引用的旧数据集注册、scope、报告缓存、分析缓存、暂存记录和重复索引。

**不可清理对象：** 两份原始数据文件、合并审计、仍被报告或任务引用的数据、未解析身份的数据。

**流程：**

1. 生成只读清理预览，展示目标、数量、磁盘占用和引用关系。
2. 统一数据集通过全部验收后，停用旧派生数据并从业务入口隐藏。
3. 保留 7 天回滚窗口并完成一次恢复演练。
4. 窗口结束后重新检查引用，只物理删除批准目标。
5. 记录操作者、时间、原因、目标和删除数量。

## 6. 业务规则

| 条件 | 系统行为 |
|---|---|
| 开始合并两份来源 | 创建新的统一数据集版本，不改写来源 |
| 两条记录映射到同一确定性订单行业务键且值一致 | 统一事实只保留 1 条，记录重复来源 |
| 两条记录业务键相同但值冲突 | AdventureWorks 优先，记录冲突字段与被排除值 |
| 只能通过金额、日期或名称推测重复 | 不自动去重，进入待复核隔离区 |
| 币种、粒度、时区或金额口径不一致 | 禁止跨源汇总，按来源展示并显式降级 |
| 非重复记录通过字段和质量契约 | 保留到统一事实层 |
| 客户专题未命中异常规则 | 显示正常状态、关键发现、分群贡献、证据和监测动作 |
| 客户字段或样本不足 | 显示数据不足，不生成异常或确定性判断 |
| 多业务事实为模拟扩展 | 显示“演示推算数据”，禁止财务核算和因果结论 |
| 页面需要技术血缘 | 在数据说明或证据详情中按需展示，不进入首屏 |
| 统一数据集未通过验收 | 禁止停用或删除旧派生数据 |
| 旧派生数据停用未满 7 天 | 允许恢复，禁止物理删除 |
| 清理目标存在有效引用 | 跳过该目标并显示引用关系 |

## 7. 输出产物

### 7.1 产品输出

- 一个可选择的统一业务数据集。
- 修复后的客户专题正常状态。
- 精简后的广告、退款和物流专题。
- 所有页面一致的数据说明与模拟披露。
- 旧数据维护、停用、恢复和清理结果。

### 7.2 数据输出

- 新的统一数据集版本。
- 来源映射表。
- 去重、冲突和隔离记录表。
- 合并质量与金额对账结果。
- 功能覆盖矩阵。

### 7.3 审计输出

- 合并审计：输入、保留、重复、冲突、隔离、金额和规则版本。
- 清理预览：目标、大小、引用和计划动作。
- 清理审计：停用、恢复或删除的目标与结果。
- 报告、任务和 Agent 继续继承统一数据身份与来源限制。

## 8. AI 行为边界

### 8.1 执行状态

- `SUCCESS`：统一数据和证据足以支持回答。
- `PARTIAL`：部分来源或专题降级，但可返回有限结论。
- `SKIPPED`：字段、口径或证据不足，不强行回答。
- `FAILED`：单次可恢复执行失败。
- `FATAL`：统一数据身份或正式事实层不可用。

### 8.2 允许

- 查询统一数据集上的注册指标和参数化工具。
- 解释客户正常状态、分群贡献和正式异常。
- 引用多业务正式结果及其演示限制。
- 生成有证据的报告摘要或任务草稿。

### 8.3 禁止

- 绕过统一数据集合同混合旧 `dataset_id`、scope 或币种。
- 修改或删除原始业务文件。
- 自行重算不同于正式事实层的数字。
- 把贡献、相关性或时序表述为已证明因果。
- 把退货关联 GMV 表述为退款损失。
- 隐藏示例来源、演示推算、质量不足或隔离事实。
- 为了回答完整而制造异常、证据或建议。

## 9. 交互设计

### 9.1 全局数据身份

- private 产品默认只显示统一数据集业务名称。
- 所有页面跳转保留统一 `dataset_id`、scope、周期和筛选。
- 标题区域使用业务语言显示数据期间、币种、质量和演示状态。
- 内部 ID 仅在“数据说明”展开后显示。

### 9.2 客户专题

- 有异常：展示正式异常、驱动、证据和建议。
- 无异常：展示绿色或中性的正常状态，并继续展示结构、贡献、证据和监测动作。
- 数据不足：展示独立的降级状态和缺失字段，不使用正常状态样式。
- 关闭证据详情后保留筛选、滚动和卡片状态。

### 9.3 多业务专题

- 首屏先展示业务结论和关键指标，不等待技术详情。
- “演示推算数据”以简短状态显示，不使用内部英文关键字。
- 数据说明按需展开，包含来源、口径、覆盖范围和不可用于财务核算的限制。
- 空模块不渲染空卡片，使用正常状态或数据不足状态替代。

### 9.4 清理维护

- 用户先看到清理预览，物理删除按钮在验收和回滚窗口前不可用。
- 每个目标显示类型、大小、引用、计划动作和恢复期限。
- 被引用或未解析的数据默认跳过。
- 操作完成后显示停用、跳过、失败和可恢复数量。

## 10. 技术约束

### 10.1 架构约束

- React + FastAPI 是唯一主产品。
- FastAPI 路由调用服务或 Presenter，不直接访问 `runtime._service`。
- 合并、去重、清理和正常状态逻辑属于显式服务、Presenter 或 `crossborder_analytics`。
- SQL 与注册指标是正式事实层；前端只负责展示和交互。
- 原始文件只读，统一数据集使用版本化 SQLite 或现有 ArtifactStore 能力原子生成。

### 10.2 性能约束

- 合并和清理不得阻塞正常页面请求。
- 统一数据集切换继续复用现有缓存与精确失效机制。
- 首屏、专题冷打开、热切换和详情展开不得低于现有核心恢复 PRD 的性能门槛。
- 数据层变化后运行 `python scripts/benchmark_sqlite.py`，记录冷/热状态与 P50/P95。

### 10.3 不支持

- 模糊实体解析或概率去重。
- 实时双向同步两份来源。
- 自动汇率换算，除非未来增加正式汇率事实和口径。
- 未经预览和回滚窗口的即时硬删除。
- 任意 SQL 或 Agent 自主修改数据库。

## 11. 异常处理

| 异常 | 用户提示 | 系统行为 | 恢复方式 |
|---|---|---|---|
| 业务键无法确定 | 部分记录无法自动去重 | 隔离记录，不做模糊匹配 | 修正映射后生成新版本 |
| 币种或金额口径冲突 | 当前来源不能合并金额 | 分来源展示并降级统一 KPI | 补充正式口径后重算 |
| 合并中途失败 | 统一数据集创建失败 | 放弃未完成版本，来源不受影响 | 修复后重新执行 |
| 合并对账不平 | 统一数据集未通过校验 | 不切换产品入口 | 排查重复、冲突或隔离记录 |
| 客户没有异常 | 当前范围未发现异常 | 展示正常经营分析 | 无需恢复 |
| 客户字段不足 | 无法完成部分客户分析 | 显示缺失字段和降级模块 | 补充数据后重算 |
| 多业务事实为模拟 | 当前结果用于演示 | 持续显示限制 | 接入真实事实后替换 |
| 清理目标被引用 | 该数据暂不能清理 | 跳过并记录引用 | 解除引用后重新预览 |
| 回滚期统一数据异常 | 已恢复旧派生数据 | 停止物理删除并恢复旧入口 | 修复统一数据后重新验收 |
| 最终删除部分失败 | 部分目标未清理 | 已删除目标不重复执行，失败目标保留 | 修复后幂等重试 |

## 13. 开发阶段规划

### Phase 1：只读基线与契约冻结

- 统计两份来源的字段、粒度、业务键、周期、币种、金额和质量。
- 运行只读合并预演，输出保留、重复、冲突和隔离清单。
- 生成旧数据集、scope、缓存、暂存记录和索引的清理预览。
- 建立客户空状态和多业务技术关键字的失败回归。

**完成闸门：** 每个合并与清理目标都有确定身份；币种、粒度和金额口径未确认项全部显式列出。

### Phase 2：统一数据集构建

- 实现标准化、质量门禁、确定性去重和 AdventureWorks 冲突优先。
- 创建新的统一 `dataset_id`、来源映射和合并审计。
- 完成行数与金额对账。

**完成闸门：** 对账差异为 0，原始文件未改变，不兼容记录未进入统一总额。

### Phase 3：单数据集全功能路由

- 让总览、普通专题、多业务、报告、任务和 Agent 使用统一数据身份。
- private 产品只展示统一业务入口，旧来源进入维护层。
- 精确失效旧来源缓存。

**完成闸门：** 功能覆盖矩阵 100% 通过，不需要切换数据集。

### Phase 4：客户与多业务体验修正

- 实现客户正常状态、关键发现、分群贡献、证据和监测动作。
- 精简三个多业务首屏并下沉技术血缘。
- 统一示例、演示推算和数据不足文案。

**完成闸门：** 客户页面不再出现有数据但分析区全空；多业务首屏无内部技术关键字。

### Phase 5：停用与回滚验证

- 完成后端、前端、浏览器和性能验收。
- 停用旧派生数据并隐藏旧业务入口。
- 执行一次恢复演练，进入 7 天观察期。

**完成闸门：** 统一数据健康，旧数据不参与新分析，恢复演练成功。

### Phase 6：物理清理

- 7 天后重新生成清理预览和引用检查。
- 删除已批准且无引用的旧派生数据。
- 写入清理审计并再次运行全功能回归。

**完成闸门：** 原始文件和合并审计完整，误删为 0，删除目标审计率 100%。
