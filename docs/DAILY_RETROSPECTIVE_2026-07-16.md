# 2026-07-16 今日总结、反思与优化

## 1. 今日目标回顾

今天的核心目标不是单独做一个可视化页面，而是在 AutoClean 基础上完成一个可复用、可追溯的跨境电商分析分支项目。

最终完成了以下交付：

- AutoClean 6.4 非破坏性分析公共层。
- 跨境电商经营总览、销售、商品、客户、区域和退货六个分析模块。
- 中文 Streamlit Dashboard。
- Excel、Markdown、DOCX 和 manifest 导出。
- Chrome、Edge 浏览器自动化连接和真实页面验收。
- 客户分群明细切换、搜索、分页与 CSV 下载。
- 两个 GitHub 仓库的版本提交、推送和 CI 验证。

当前测试结果：

- CrossBorder AI Analytics：16 项测试通过，4 项浏览器测试默认跳过。
- AutoClean：4 项测试通过。
- AutoClean GitHub Actions：通过。

## 2. 今天做得比较好的地方

### 2.1 坚持了数据安全边界

原始数据只读，清洗、类型转换、字段映射和币种换算都发生在分析视图中。没有为了快速得到结果而自动删除重复订单、填充核心字段或修改原始文件。

这一点保证了后续报告、SQL 查询和审计能力可以建立在可信数据血缘上。

### 2.2 将通用能力和场景能力分开

文件读取、数据契约、模块执行、证据、汇率和导出放在 AutoClean；跨境项目只维护电商字段契约、指标和业务规则。

这比把所有逻辑堆在 Streamlit 页面里更有长期价值。未来增加库存、广告或物流分析时，可以复用同一底座。

### 2.3 没有把“相关”写成“原因”

当前建议使用“贡献、关联、建议检查”等措辞，并绑定证据编号。缺少广告、成本或退款字段时，不生成对应结论。

这让产品从普通报表更接近可信的商业分析工具。

### 2.4 最终解决了客户明细的实际使用问题

客户分群图只能说明结构，运营人员真正需要的是可以查看和导出具体客户。最终实现保留固定 RFM 统计口径，同时让明细表独立切换客户类型。

这次修正说明：分析页面不能只回答“发生了什么”，还需要提供“接下来处理哪些对象”。

### 2.5 建立了真实浏览器验收能力

通过 Chrome 和 Edge 的独立调试端口，能够读取真实 URL、DOM、点击、输入、下载和截图。侧栏问题不再依赖猜测 CSS，而是可以稳定复现和回归。

## 3. 今天没有做好的地方

### 3.1 错误理解了客户分群需求

用户希望切换查看不同类型客户的明细，我最初把“客户分群不能调节”理解成需要自定义 RFM 阈值，因此增加了统计规则控制。

这次理解偏差带来了两个问题：

- 修改了用户并不希望改变的统计口径。
- 没有第一时间解决“前500行全部是 VIP 客户”的真实问题。

根因不是技术实现，而是没有先区分两个概念：

- **分析口径调整**：改变客户如何被分类。
- **结果明细筛选**：在固定分类结果中查看某类客户。

后续遇到“调节、筛选、切换、自定义”等词时，必须先确认它影响计算模型还是只影响展示结果。

### 3.2 侧栏问题第一次修复缺少真实 DOM 依据

侧栏收起后无法展开，第一次处理时主要依据 Streamlit 的常见结构和 CSS 推测，没有先在真实浏览器中确认按钮是否存在、是否被隐藏、是否被遮挡。

结果是改动没有命中根因。后续建立 CDP + Playwright 后才确认 `stExpandSidebarButton` 与 `stToolbar` 的实际关系。

反思：前端兼容问题不能只看源码和截图。涉及点击失效、层级、响应式布局或第三方组件时，必须先获取 DOM、计算样式和点击结果。

### 3.3 过早关注统计功能，忽略运营动作

第一版客户页已经有分群数量和图表，但没有充分考虑用户下一步要做客户维护、唤回或营销触达。

类似不足在商品模块仍然存在：页面目前只展示前500个商品，长尾商品虽然参与计算，但不便于逐个排查和导出。

以后每个分析模块都要同时验收三层能力：

1. 汇总指标是否正确。
2. 结论和证据是否可信。
3. 用户能否定位、导出或处理对应明细。

### 3.4 仓库和依赖结构没有在开发前固定

跨境目录最初存在一个空 `.git`，Git 实际解析到了 `D:\projects` 的父级仓库。直到发布前才发现仓库边界异常。

同时，跨境项目通过 `-e ../AutoClean-v1` 使用底座，适合本地联调，但不适合独立 CI 和标准部署。

这说明项目初始化阶段应该先完成：

- 仓库根目录确认。
- 远程仓库和分支策略。
- 包依赖和版本策略。
- CI 安装路径验证。

### 3.5 测试数量与项目规模仍不匹配

现有测试保护了核心样例指标和关键交互，但还缺少：

- 每个分析模块的独立边界测试。
- 大文件和性能基准测试。
- Linux 环境测试。
- 报告分页、字体和图表渲染回归。
- 在线汇率端点的可选集成测试。
- 安全、恶意文件和异常编码输入测试。

当前测试证明 MVP 主路径可用，但还不能证明生产环境稳定。

## 4. 可复用的改进方法

### 4.1 需求确认改为“对象、动作、影响范围”三问

开始实现前明确：

1. 用户要操作的对象是什么，例如统计规则、汇总图还是客户明细。
2. 用户要执行的动作是什么，例如重新计算、筛选、导出还是修改数据。
3. 操作应该影响哪些区域，哪些区域必须保持不变。

客户明细需求如果用这三问表达，就是：操作对象为客户清单，动作为切换和导出，只影响明细表，分群统计图必须保持不变。

### 4.2 页面验收增加“业务闭环检查”

每个模块交付前检查：

- 能否从汇总定位到明细。
- 明细是否完整，而不是静默截断。
- 是否支持搜索、筛选和排序。
- 是否能导出当前结果。
- 导出结果是否与页面筛选一致。
- 页面操作是否改变了不应改变的统计口径。

### 4.3 前端问题采用证据驱动调试顺序

固定顺序如下：

1. 在目标浏览器复现。
2. 记录 URL、视口、DOM 和截图。
3. 确认元素存在性、可见性、层级和点击区域。
4. 做最小修改。
5. 在 Chrome、Edge、桌面和窄屏重复验证。
6. 将复现步骤转为 Playwright 回归测试。

### 4.4 分析模块统一采用四层结构

- **契约层**：字段、类型、粒度和语义。
- **计算层**：指标、阈值、样本门槛和状态。
- **证据层**：公式、字段、周期、样本和证据 ID。
- **操作层**：明细定位、筛选、下载和后续处理。

以后新增广告、库存、物流或 SQL 模块时沿用这四层结构。

### 4.5 发布前执行仓库检查清单

- `git rev-parse --show-toplevel` 是否指向正确目录。
- `git status` 是否只有本次范围内文件。
- 缓存、输出、浏览器资料和密钥是否被忽略。
- `git diff --check` 是否通过。
- 单元测试、AppTest 和必要的浏览器测试是否通过。
- README、CHANGELOG 和路线图是否同步。
- 远程提交、CI 和 PR 是否真实存在。

## 5. 下一次开发方式优化

### 开始前

- 先写一页验收口径，明确哪些指标和页面区域不能被改动。
- 确认仓库边界、依赖来源、测试命令和发布目标。
- 对截图类需求先在真实浏览器中定位目标组件。

### 开发中

- 先写纯函数和模块测试，再连接 Streamlit 状态。
- 每完成一个业务模块，同时补汇总、证据和明细操作。
- 对任何 `.head()`、抽样或分页明确标注它是否会丢失用户可见数据。
- 只在显示副本中汉化和搜索，不改变分析 DataFrame。

### 完成前

- 用样例数据核对固定指标。
- 验证缺字段、空数据、零分母、重复订单和低样本情况。
- 在 Chrome 和 Edge 中完成桌面、窄屏和下载测试。
- 从一个干净目录重新安装并启动，验证项目不依赖开发机偶然状态。

## 6. 明日优先建议

下一步最值得做的不是增加更多图表，而是完成以下工程闭环：

1. 将 AutoClean 6.4 PR 合并并发布为可固定版本的私有包。
2. 让跨境项目在没有相邻目录的环境中可以独立安装。
3. 建立跨境项目 CI 和依赖锁文件。
4. 完善可选字段映射并保存映射模板。
5. 取消商品明细500行限制，增加完整筛选和导出。

完成这五项后，再进入 DuckDB/SQL、权限、安全和多数据源阶段，整体返工风险会明显降低。

## 7. 今日结论

今天最大的收获不是完成了多少页面，而是明确了这个项目应该遵守的开发原则：数据不能被悄悄修改，指标不能脱离证据，统计不能代替操作，前端问题不能依靠猜测，发布不能停留在本地成功。

当前 MVP 已经具备继续工程化的基础，但下一阶段应优先解决依赖、CI、完整明细和部署问题，而不是立即堆叠 AI 功能。
