# CrossBorder 项目技术与产品审计

审计日期：2026-07-21  
审计范围：仓库源码、SQL、测试、文档、部署配置、样例数据和本地运行产物  
排除范围：`node_modules`、构建产物和缓存不作为代码质量样本，但统计其体积与运行影响

## 审计证据

- 业务分析源码约 7,464 行，API 约 1,936 行，前端源码约 3,017 行，测试约 1,391 行。
- 14 个命名 SQL；12 个注册指标、9 条异常规则、8 条建议规则。
- 样例数据 34,500 条订单、17 个原始字段，时间覆盖约两年。
- 完整回归：64 passed、6 skipped，耗时 265.57 秒；跳过项均为外部浏览器 E2E。
- 前端：3 个 Vitest 用例通过；生产构建通过，JS 产物 1.65 MB，gzip 540 KB。
- 10 万行基准：完整 Phase 2 流水线 95.883 秒，兼容链路 9.633 秒，回退 895.3%。
- API 实测：未缓存专题请求 13.69 秒，同请求缓存后 1.38 秒。
- 审计环境默认数据库 957.4 MB，包含 103,512 条订单、533,773 条指标快照和 206,517 条实体评估。

## 2. 技术栈分析

|层|技术|审计结论|
|---|---|---|
|数据输入|CSV/XLSX、AutoClean 6.6|支持字段映射、类型转换、质量问题和只读分析视图；Web 未开放真实导入|
|数据处理|Python、pandas、NumPy|业务规则表达清晰，但大量全量 DataFrame 聚合限制规模和响应时间|
|存储|SQLite、WAL、版本化 dataset_id|适合本地单用户；数据集隔离、幂等和事务边界较完整，派生对象体积失控|
|查询|14 个参数化命名 SQL|避免任意 SQL，具备审计记录；过滤维度与查询目录仍是固定集合|
|分析域|Dataclass、Catalog、规则引擎|指标、异常、诊断、建议、证据对象化程度高|
|后端|FastAPI、Uvicorn、SSE、httpx|接口可用，但响应模型大多是 `unknown`，长任务和并发机制不足|
|前端|React 18、TypeScript、TanStack Query、ECharts、Radix、Tailwind|主体验完整；测试少、包体大，页面组件过重|
|兼容界面|Streamlit、Plotly、AgGrid|功能覆盖广，但与 React 双轨维护增加重复逻辑|
|报告|openpyxl、python-docx、Matplotlib|四种输出使用同一分析包，证据附录较完整|
|测试|pytest、Vitest、Playwright|Python 覆盖较好；React E2E、CI、覆盖率和性能门禁缺失|
|部署|Docker 多阶段构建、PowerShell 启动|单机部署路径存在；未发现 CI/CD、健康编排、备份迁移或生产运维方案|

## 3. 核心模块说明

|模块|职责|成熟度判断|
|---|---|---|
|AutoClean + Contract|读取、映射、字段契约、质量问题、原始数据只读|较完整，但外部 Git 依赖影响离线复现|
|SQLite 数据层|版本化订单、命名 SQL、数据集隔离、查询审计|基础扎实；单表订单模型和存储膨胀限制扩展|
|传统分析模块|经营、销售、商品、客户 RFM、市场、市场品类、退货|可用，适合规则型本地分析|
|Metrics Engine|12 个指标，按 global/market/category/SKU 和周期生成快照|契约专业，但全量快照策略是主要性能瓶颈|
|Rules Engine|9 条版本化异常规则、样本与质量门槛|可审计，但阈值仅在样例数据上验证|
|Diagnosis Engine|GMV、AOV、利润率、退货率和贡献率数学分解|能约束因果措辞；真实业务归因深度受字段限制|
|Recommendation Engine|诊断状态、保护指标、负责人、验证周期和停止条件|比普通 BI 强，但动作仍偏规则模板，缺少结果回写校准|
|Evidence / Insight|SQL 版本、参数、摘要哈希、证据回放、优先级排序|是项目最明确的差异化基础|
|Opportunity Engine|市场增长、产品机会和行动项|规则完整度较高，真实业务收益未验证|
|FastAPI Runtime|将分析包转换为四页 DTO|功能集中但 1,304 行，重复计算和重复业务规则明显|
|React 产品|Overview、五主题、DataHub、AI 分析师|前两页完成度高；DataHub 和任务闭环不完整|
|Agent 层|会话、SSE、受控上下文、可选模型调用|属于受控问答原型，不是真正的工具调用 Agent|

## 4. 数据流说明

```text
CSV/XLSX（只读）
  → AutoClean 读取、字段映射、类型转换、质量检测
  → DatasetContext 规范订单视图
  → 汇率换算与领域校验
  → SQLite orders（dataset_id 隔离）
  → 命名 SQL / metric_facts_v1
  → 传统分析模块 + Metrics Engine
  → MetricSnapshot
  → Anomaly → Diagnosis → Recommendation
  → EvidenceBundle → Insight / Opportunity / ActionItem
  → ArtifactStore 持久化
  → FastAPI Runtime DTO
  → React / Streamlit / Excel / DOCX / Markdown / manifest
```

Agent 当前实际数据流：

```text
用户问题
  → 关键词判断“需要哪些工具名称”
  → runtime.overview() 一次性计算完整分析包
  → build_decision_brief()
  → 前端显示模拟工具进度事件
  → 确定性答案，或把同一结构化结果交给模型单次润色
  → 答案合同补充数据集、周期、证据和限制
```

该流程没有真实工具注册协议、模型自主选工具、逐步调用、观察结果后再规划，也没有跨轮业务记忆参与推理。

## 5. 当前已有能力清单

- CSV/XLSX 读取、别名映射、订单粒度冲突检测和领域规则校验。
- 源币种确认、在线/上传汇率、基准币种金额与汇率血缘。
- 数据质量总分、维度质量、字段健康、能力地图和补数建议。
- SQLite 数据集版本、幂等入库、事务回滚、WAL、索引和查询审计。
- GMV、订单、客单价、销量、客户、利润、利润率、退货率、增长率、商品/市场贡献、市场质量分。
- 完整周期识别、零分母保护、低样本门槛和异常抑制。
- 经营总览、五主题分析、商品详情、客户 RFM、市场策略、增长机会和退货风险。
- 异常、数学贡献诊断、建议、保护指标、验证周期、停止条件和证据绑定。
- 风险/洞察/数据健康 Streamlit 工作区和 React 四页产品框架。
- URL 分析筛选、明细搜索分页、CSV 导出、Drawer 和报告预览。
- Excel、Markdown、DOCX、manifest 报告及报告图表。
- 私有模式任务状态、Agent 会话/消息/事件 SQLite 持久化。
- OpenAI 兼容模型与本机 CC Switch 配置导入，密钥不返回前端。
- Docker 单容器构建和命令行分析入口。

## 6. 缺失能力清单

### 产品闭环

- Web 数据导入、字段映射、更新和删除未实现；DataHub 的导入与更新按钮禁用。
- DataHub“指标目录”为空，导入记录和汇率配置是静态预览；质量分 98/96 为 Runtime 硬编码。
- React 任务仅能标记“处理中”，不能完整维护责任人、截止日期、处理结论和结果指标。
- 建议执行后的结果回写、效果评估、规则校准和历史复盘没有闭环。
- 报告接口未接收当前页面日期、市场、品类筛选，页面与下载报告可能口径不一致。
- 没有定时刷新、文件监控、增量导入、数据源连接器和失败重试。

### 商业分析

- 缺少真实成本、退款额、库存、广告、活动、渠道、价格事件、退货原因和物流节点。
- 无法计算净利润、真实退款损失、ROAS、库存周转、缺货影响、渠道归因和活动增量。
- Topic 页面另有一套 Runtime 内临时比较、异常和动作逻辑，没有统一消费版本化 Rules/Diagnosis/Recommendation 对象。
- 异常 Top5 可能同时包含不利变化和改善对象，业务命名与阈值仍需校准。
- 缺少可配置指标、规则、阈值和业务事件日历。

### AI Agent

- 没有真正的工具 schema、工具执行循环、规划器、反思、取消、重试和预算控制。
- 对话历史被保存但未进入后续模型上下文，不构成多轮业务记忆。
- 进程重启后已持久化 run/event 不能由 SSE 重新恢复，内存运行状态会丢失。
- 没有 Agent 事实一致性、引用正确率、建议安全性和问题集评测框架。
- 没有 prompt injection、敏感字段、PII、工具权限和模型输出审计策略。

### 企业能力

- 无身份认证、RBAC、多租户、团队协作、审批、通知和审计权限。
- 无备份恢复、数据保留、归档压缩、迁移回滚和容量管理。
- 无 API 限流、并发控制、任务队列、分布式锁和生产级可观测性。
- SQLite 单机架构不适合多用户高并发和长期大规模历史快照。

# 二、项目优势

1. 原始数据只读、数据集版本隔离和证据可回放，可信度设计明显高于普通作品集。
2. 指标、异常、诊断、建议、证据和洞察形成稳定领域对象，不是散落在页面中的计算。
3. 数据质量不仅给分，还输出能力地图、不可回答结论和补数计划。
4. 异常规则包含完整周期、样本门槛、质量门槛、保护指标和恢复条件。
5. 诊断明确区分数学贡献与真实因果，避免把广告、库存和活动原因写成已证实结论。
6. 建议带负责人、目标指标、保护指标、验证周期和停止条件，业务结构优于普通 BI 告警。
7. SQL 与 pandas 有对账测试，数据库失败不会静默切换计算路径。
8. 报告、Dashboard 和 Agent 简报消费同一批核心分析对象，具备未来统一交付基础。
9. React 产品的 Overview 和 Topic 已具备较完整的运营阅读与下钻体验。

# 三、项目短板

1. 性能当前不可接受。10 万行接近 96 秒，34,500 行专题冷请求仍约 14 秒。
2. 数据中心不是完整功能：无法从 Web 导入、映射、更新数据，部分导航是空内容或静态内容。
3. 默认数据库快速膨胀到接近 1 GB，没有清理、归档和 scope 生命周期策略。
4. Topic 分析绕开正式 Rules/Diagnosis 链，形成第二套经营判断来源。
5. 当前 Agent 是“预计算分析 + 答案包装”，不是能自主调用工具的 Agent。
6. 建议没有进入完整任务执行和结果评估闭环，不能证明产生经营收益。
7. 关键商业字段不足，无法支持净利润、广告效率、库存和真实退款损失分析。
8. React 自动化测试明显不足，仓库没有针对主产品的真实浏览器回归套件。
9. 无 CI、生产可观测性、身份权限和长任务基础设施。
10. 版本、PRD 阶段、README、前端包和 Python 包标识不一致，工作区大量改动未提交。

# 四、与行业标准对比

|对比对象|当前水平|
|---|---|
|普通数据分析项目|明显高于。具备数据契约、数据库、规则、证据、报告和产品界面，不是 Notebook 或图表集合|
|Power BI / Tableau 类 BI|垂直语义、证据边界和建议规则更强；连接器、刷新、自由探索、权限、协作和成熟性能远弱于成熟 BI|
|企业级数据分析平台|明显低于。缺少数据接入平台、调度、血缘平台、权限、多租户、可观测性、容量治理和 SLA|
|AI 商业分析 Agent|处于 Agent-ready 原型。已有受控分析对象，但尚未实现工具调用、规划、记忆、评测和安全治理|

当前位置：高质量垂直分析 Demo，具备商业 MVP 的架构骨架，但尚不是可交付给真实团队持续使用的产品。

# 五、未来升级优先级

## P0：必须马上优化

1. 将 10 万行完整流水线压到 15 秒以内、常用筛选压到 3 秒以内：拆分计时，避免每个 scope 全量生成和写入快照，按需计算、批量写入并增加保留策略。
2. 统一 Topic 与 Catalog/Rules/Diagnosis/Recommendation 数据源，删除 Runtime 内第二套异常和动作逻辑。

# 六、最终评价

## 1. 如果这是一个创业项目，投资人会怎么看？

技术型投资人会认可可信分析、领域模型和证据链，但不会仅凭当前版本判断产品成立。主要质疑会是：没有真实客户与留存数据、数据接入未完成、响应速度不可用、Agent 名称大于实际能力、没有证明建议能创造收益。当前更像值得继续验证的 founder prototype，不是已经形成 PMF 的软件业务。

## 2. 如果这是一个求职项目，竞争力如何？

对数据产品、分析工程、Python 后端和 AI 应用原型岗位有较强竞争力，尤其是指标契约、质量门槛、证据边界和报告闭环。若用于高级后端、平台架构或 Agent 工程岗位，面试官会追问 895% 性能回退、无 CI、数据库膨胀、双轨逻辑和伪工具调用；这些问题必须能解释并给出重构结果。

## 3. 如果继续开发 6 个月，最高可以达到什么级别？

如果前 2 个月优先解决性能、真实数据接入、场景测试和统一分析语义，中间 2 个月完成任务闭环与可观测性，后 2 个月在真实商家数据上校准规则，最高可以达到“可供少量客户试点的垂直商业分析产品”或“企业内部单团队分析工具”。在没有连接器、权限、并发平台、真实业务验证和 Agent 评测的情况下，6 个月内不应宣称企业级数据平台或成熟 AI 商业分析 Agent。
