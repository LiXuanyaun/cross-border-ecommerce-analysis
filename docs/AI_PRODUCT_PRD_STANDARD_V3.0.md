# AI 产品 PRD 编写规范 v3.0

**适用范围：** AI 产品、Agent、数据工具、SaaS、自动化工具和企业应用
**目标：** 让 AI Coding 工具不仅交付“能运行的功能”，还交付数据正确、流程完整、升级可靠、可验证的产品。

## 1. v3.0 相比 v2.0 的关键变化

v2.0 已覆盖商业目标、用户场景、输入、业务规则、输出、边界和基础验收，但“验收”更接近功能清单。

v3.0 新增强制要求：

1. 每个核心功能必须绑定完整用户流程，不能只验接口或单个页面。
2. 测试必须同时覆盖全新环境和已有历史数据的升级环境。
3. 页面、接口、数据库、报告和 Agent 必须验证同一数据范围与同一业务口径。
4. 必须定义禁止出现的结果，例如重复数据、跨数据集混算和无证据结论。
5. 关键流程未通过、被跳过或没有验证证据时，不得发布。

## 2. 标准 PRD 结构

所有正式 PRD 使用以下结构：

1. 核心定义与产品边界
2. 商业目标与成功指标
3. 用户与核心场景
4. 输入数据与数据契约
5. 核心用户流程
6. 业务规则与决策逻辑
7. 输出产物
8. AI 行为边界
9. 交互与状态设计
10. 技术约束与性能目标
11. 异常处理与恢复
12. 验收标准
13. 完整功能测试与发布门禁
14. 依赖、风险与开放问题
15. 开发阶段与优先级
16. PRD 自评与决策记录

## 3. 每项需求的标准写法

每项核心需求必须包含以下内容：

```markdown
### FR-001 功能名称

用户目标：
业务价值：
前置条件：
输入：
完整操作步骤：
页面结果：
数据结果：
输出产物：
异常与恢复：
禁止结果：
验收证据：
自动化测试层级：单元 / 契约 / 集成 / 端到端 / 升级回归
```

只写“支持上传”“支持分析”“可以导出”不算完整需求。

## 4. 数据类产品的强制数据契约

PRD 必须明确：

- 数据来源、文件或接口类型、版本和所有者。
- 数据粒度，例如一行一订单或一行一商品。
- 唯一键、关联键和允许的重复规则。
- 金额、币种、时区、周期和空值语义。
- 原始数据、标准化数据、展示数据和模拟数据的边界。
- 数据集编号、分析范围编号和证据编号如何贯穿系统。
- 缺字段、低质量、弱关联和不完整周期如何降级。
- 哪些问题阻断全局，哪些问题只停用一个分析模块。

禁止把“字段名相同”视为“业务含义相同”。

## 5. 核心用户流程

PRD 必须按用户任务描述流程，不按数据库、接口和前端模块拆分。

每条 P0 流程至少覆盖：

```text
进入产品
-> 提供或选择数据
-> 系统校验
-> 用户确认
-> 生成分析
-> 查看详情与证据
-> 导出或形成任务
-> 刷新或重启后继续使用
```

流程中每一步都要定义成功、跳过、失败和恢复结果。

## 6. 业务规则

业务规则使用“条件 -> 行为 -> 证据 -> 限制”的格式：

|字段|说明|
|---|---|
|条件|规则何时适用|
|行为|系统计算、展示或阻断什么|
|证据|结论来自哪些数据和公式|
|限制|何时不得生成该结论|

缺少证据时必须明确跳过，不能使用 AI 补全业务事实。

## 7. 输出产物

每个输出必须定义：

- 名称和格式。
- 页面、章节、工作表或字段结构。
- 使用的数据集和分析范围。
- 指标、规则、质量状态和证据标识。
- 与其他输出的一致性要求。
- 空数据、失败和降级时的输出。

## 8. AI 行为边界

必须分别写清允许、禁止和需要人工确认的行为。

最低要求：

- AI 只能使用注册工具和已验证数据。
- AI 不得修改原始数据、指标定义和质量状态。
- AI 不得把相关性写成因果性。
- AI 不得在缺字段时推测利润、退款损失或经营原因。
- 对外部操作、删除、覆盖和发送必须取得明确确认。
- 工具失败时必须确定性降级，不能伪装成功。

## 9. 异常与恢复

每个核心流程必须覆盖：

- 输入无效。
- 部分字段缺失。
- 网络或模型不可用。
- 数据库写入失败。
- 页面刷新和进程重启。
- 重复提交。
- 升级或迁移失败。
- 用户取消或回退。

异常定义必须包含用户提示、数据是否写入、如何恢复以及是否允许重试。

## 10. 基础验收标准

### 功能验收

- 用户可以完成目标任务，而不只是看到入口。
- 所有按钮、筛选、详情、导出和返回路径可用。
- 刷新和重启后状态符合定义。

### 数据验收

- 指标与基准计算一致。
- 数据来源和转换可追溯。
- 不同数据集、用户、周期和币种不会混算。
- 重复操作保持幂等，不产生重复事实。

### 商业验收

- 产品能回答目标用户的核心问题。
- 建议包含对象、动作、依据和限制。
- 缺少证据时明确说明不能回答。

### 体验验收

- 桌面和约定窄屏可完成核心流程。
- 加载、空状态、警告、失败和恢复状态完整。
- 文本、控件和图表不重叠，不出现不可操作入口。

## 11. 完整功能测试

完整功能测试不是一种测试，而是以下测试共同形成的产品证据：

|层级|验证内容|不能替代什么|
|---|---|---|
|单元测试|单个公式、规则和函数|不能证明完整流程可用|
|数据契约测试|字段、粒度、币种、唯一键和关联|不能证明页面与输出一致|
|集成测试|导入、数据库、分析、报告之间的连接|不能证明真实用户操作可用|
|浏览器端到端测试|用户实际点击完成任务|不能证明历史数据库可升级|
|持久状态回归|重启、重复导入、升级和清理|不能只用全新临时数据库替代|
|跨产物一致性测试|页面、接口、报告和 Agent 数字一致|不能只检查格式存在|
|失败与恢复测试|失败不写脏数据且能够恢复|不能只检查成功路径|

## 12. 端到端用例模板

每条 P0 用户旅程必须写成可执行用例：

```markdown
### E2E-001 用例名称

优先级：P0
测试环境：全新 / 已有历史数据 / 升级后
前置数据：
用户步骤：
预期页面结果：
预期数据库结果：
预期报告或 Agent 结果：
禁止结果：
刷新或重启后的结果：
失败后的恢复方式：
自动化脚本：
验收证据：日志 / 截图 / 数据查询 / 导出文件
```

## 13. 持久状态与升级测试矩阵

数据类产品至少覆盖：

|场景|必须验证|
|---|---|
|全新安装|首次启动和默认数据正确|
|首次导入|只生成一个正式数据集|
|重复导入|复用原数据集，不重复写事实|
|切换数据集|页面和输出全部切换，不保留旧范围|
|刷新与重启|身份、筛选和任务状态符合定义|
|旧版本升级|迁移不丢数据、不重复数据、不改变口径|
|维护和清理|不删除仍被引用的数据，不产生孤立记录|
|失败后重试|没有半成品数据，重试结果幂等|

## 14. 跨页面与跨产物一致性

同一次分析必须验证以下标识和结果一致：

- 数据集编号。
- 分析范围编号。
- 周期和筛选。
- 币种。
- 质量状态。
- 指标值和公式版本。
- 证据和限制。

Dashboard、详情、导出、报告、任务和 Agent 任一处不一致，核心流程不得验收通过。

## 15. 发布门禁

以下任一情况发生时禁止发布：

- P0 用户旅程失败或被跳过。
- 只在全新数据库测试，没有升级数据库测试。
- 出现重复数据集、重复事实或孤立关联记录。
- 页面、报告和 Agent 使用不同数据范围。
- 真实数据与模拟数据没有清晰分开。
- 核心指标没有基准对账。
- 浏览器测试只检查页面打开，没有完成用户操作。
- 失败路径可能留下部分写入。
- 没有记录本次实际运行的测试和未运行项。

## 16. Definition of Done

功能只有同时满足以下条件才算完成：

- [ ] 用户目标已经实现。
- [ ] 数据和业务规则已经实现。
- [ ] 禁止行为已经被测试阻止。
- [ ] 单元、契约和集成测试通过。
- [ ] P0 浏览器端到端流程通过。
- [ ] 全新数据库和升级数据库均通过。
- [ ] 页面、报告、导出和 Agent 一致。
- [ ] 性能和失败恢复达到要求。
- [ ] 没有跳过关键测试。
- [ ] 文档、代码和当前产品能力一致。

## 17. 开发阶段规则

1. 每个阶段只交付一个可独立验收的用户闭环。
2. 数据身份、指标口径和持久化变更必须先补测试再扩展页面。
3. 新功能不得依赖未解决的 P0 数据一致性问题。
4. 每次发布都必须记录通过项、失败项、跳过项和剩余风险。
5. “测试通过”只能描述本次实际执行的范围，不能引用旧结果代替。

## 18. PRD 自评与开放问题

正式进入开发前，PRD 必须完成以下自评：

- 证据最充分的部分是什么。
- 最薄弱、最依赖推测的部分是什么。
- 哪些内容是“假设”，需要怎样验证。
- 哪些内容是“开放问题”，由谁在什么时候决定。
- 如果关键假设错误，哪些需求需要停止或调整。
- 下一步最重要的确认动作是什么。

禁止为了让 PRD 看起来完整而自行补造用户证据、商业指标、技术结论或批准状态。
