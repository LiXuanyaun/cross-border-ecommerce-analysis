## 2. 可复用经验

### 2.1 先固定数据契约，再写分析模块

业务分析最危险的问题不是公式写错，而是数据粒度和字段语义不清。应先明确：

1. 一行代表什么业务对象。
2. 哪些字段是核心字段，缺失时必须停止。
3. 哪些字段只影响单个模块，缺失时允许跳过。
4. 金额字段代表收入、利润额、利润率还是成本。

本项目将重复 `order_id` 视为订单粒度冲突，不自动去重。这一模式可以复用于库存、广告、物流和财务分析场景。

### 2.2 原始数据、分析视图、展示副本必须分层

- 原始数据：只读，负责追溯和哈希校验。
- 分析视图：类型转换、字段标准化、币种换算和指标计算。
- 展示副本：中文列名、中文枚举、格式化和搜索结果。

分层后，汉化和页面筛选不会改变计算口径，也不会污染导出和后续 SQL/API 接口。

### 2.3 模块级降级比整条流水线失败更适合分析产品

缺少利润字段时，经营规模和客户分析仍然可以继续。统一使用 `SUCCESS / SKIPPED / FAILED / FATAL`，能让系统明确区分“可用”“证据不足”“模块异常”和“数据不可分析”。

### 2.4 结论必须是“证据 + 阈值 + 措辞边界”

规则型建议至少需要：

- 稳定证据 ID；
- 计算公式和原始字段；
- 样本量与时间范围；
- 触发阈值；
- 避免因果暗示的业务措辞。

例如退货金额只能称为“退货关联 GMV（成交总额）”，没有退款额、成本和退款状态时不能称为真实损失。

### 2.5 统计图和操作明细要解耦

统计图回答“整体结构是什么”，明细表回答“下一步处理谁”。客户类型筛选只应影响客户清单，不应重新定义 RFM 分群或改变统计图。类似模式也适用于异常订单清单、待补货商品和高退货地区。

### 2.6 UI 问题必须在真实浏览器中复现

Streamlit AppTest 适合验证组件状态，但无法替代真实 DOM、CSS、下载和响应式布局验证。可靠流程是：

1. 单元测试验证计算和纯函数。
2. AppTest 验证 Streamlit 状态流。
3. Playwright 同时验证 Chrome、Edge、桌面和窄屏。
4. 对关键交互重复执行，避免只验证一次成功。

## 3. 当前项目评价

### 3.1 已经做好的部分

- **业务边界清楚**：不会在缺字段时强行计算，不会生成无依据结论。
- **分析口径可靠**：核心样例指标、完整月份、RFM、汇率和低样本规则均有测试保护。
- **可追溯性较强**：报告、表格和建议可以回到证据 ID、字段和源文件哈希。
- **模块隔离合理**：AutoClean 提供通用能力，跨境仓库只维护领域契约和业务模块。
- **交付面完整**：同一分析结果可在 Dashboard、Excel、Markdown、DOCX 和 JSON 中复用。
- **本地演示可用**：样例数据无需配置即可看到完整经营结果，客户明细已经能支持后续运营处理。

### 3.2 尚未做好的部分

- **部署方式仍是开发态**：跨境项目通过 `-e ../AutoClean-v1` 依赖相邻目录，单独克隆后不能直接安装。
- **持续集成尚未闭环**：跨境仓库没有可独立运行的 CI，真实浏览器测试也只在本地按需执行。
- **权限与数据安全不足**：当前为本地单用户应用，没有登录、角色、审计日志、脱敏和数据保留策略。
- **大数据性能有限**：pandas + Streamlit 适合当前 3.45 万行样例，但百万级订单需要列式存储、增量计算和查询引擎。
- **字段映射能力不完整**：上传页只显式映射核心金额和日期字段，自定义命名的可选字段缺少完整映射体验。
- **商品明细仍截断**：页面当前只展示 GMV 前 500 个商品，虽然比客户问题影响小，但会限制长尾商品排查。
- **报告排版缺少固定回归**：已验证章节和内容，但页数、分页、字体替换和图表清晰度尚未做像素级回归。
- **可观测性不足**：没有结构化日志、执行耗时、模块错误率、缓存命中率和数据质量趋势。
- **版本和发布管理不足**：尚未建立 changelog、语义化发布、制品归档和依赖兼容矩阵。
- **业务深度仍属 MVP**：没有成本拆解、退款状态、库存、广告、渠道、店铺和物流节点数据，无法回答真实净利润和归因问题。

## 4. 工程化路线图

### P0：可复现、可发布、可维护（1-2 周）

1. 将 AutoClean 发布为私有 Python 包或固定 Git tag，移除跨境项目对相邻目录的强依赖。
2. 为跨境仓库建立 CI：Python 3.10-3.12、单元测试、AppTest、ruff、类型检查和导出冒烟测试。
3. 固定依赖锁文件，补充 Windows/Linux 安装验证和一键启动脚本。
4. 完整实现所有可选字段的映射、语义确认和映射模板保存。
5. 移除商品前 500 行限制，使用服务端分页或按条件导出长尾商品。
6. 增加结构化日志、模块耗时、缓存命中和错误上下文，不在日志中泄露客户明细。
7. 建立 `CHANGELOG`、版本 tag、发布检查清单和回滚说明。

### P1：从演示工具到可试用产品（2-4 周）

1. 容器化部署，区分开发、测试、生产配置。
2. 增加登录、角色权限、文件隔离、审计日志、客户标识脱敏和自动清理策略。
3. 使用 DuckDB/Parquet 建立本地分析层，为后续 SQL 查询和百万级数据做准备。
4. 增加任务队列和进度状态，避免大文件分析阻塞 Streamlit 会话。
5. 建立数据质量评分、字段覆盖率、异常趋势和数据契约版本迁移。
6. 为 Excel、Markdown、DOCX 做快照测试和真实办公软件打开验证。
7. 增加运营清单工作流：标签、负责人、处理状态、备注和处理结果回写到独立业务表。

### P2：深化商业分析（1-2 个月）

1. 接入订单明细、退款、成本、库存、广告、渠道、物流节点和店铺维度。
2. 建立贡献利润、退款净损失、库存周转、广告效率和履约时效等指标体系。
3. 增加同期、同比、移动平均、异常检测和可解释预测。
4. 支持多店铺、多币种、多时区和统一商品/客户主数据。
5. 建立语义层和受控 SQL 查询，复用统一指标定义，禁止绕过权限访问原始敏感字段。
6. 在证据检索和权限边界内增加自然语言问答，回答必须引用证据 ID，无法验证时明确拒答。

### P3：生产级平台（持续演进）

1. API/任务服务与前端解耦，支持异步分析和水平扩展。
2. 建立对象存储、元数据数据库、数据目录、血缘、租户隔离和密钥管理。
3. 增加监控告警、SLO、备份恢复、灾难演练和安全扫描。
4. 建立指标认证、分析审批、报告签发和业务动作效果闭环。
5. 对规则、模型和建议做离线评估、灰度发布、漂移监测和人工复核。

## 5. 下一迭代建议

下一迭代不建议立即接入 LLM。优先完成 P0 中的包发布、CI、依赖锁定、完整字段映射和商品明细分页。这五项会显著降低安装失败、指标漂移和“页面能看但无法继续处理”的风险，也是后续 SQL、预测和多店铺能力的共同前提。
